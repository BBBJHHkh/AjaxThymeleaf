# Copilot 试样书过长时：Token 节约与精度提升最佳实践

作成：2026-10-09
定位：面向日本大型金融 IT 现场（证券 / 银行 / 保险 / JA・共济类严谨项目）的实战手册。不是 Copilot 功能介绍，而是回答一个具体问题——**试样书（仕様書）又长又多时，怎么喂给 GitHub Copilot 才能既省 Token、又不丢细节、不产生幻觉。**
案例：全部以本 PoC 的真实案件 `JOJAMPG01W010`（JA向けマイページメニュー、PL / BL 详细设计）为例，数字均为实测，不是示意数字。
关联文档：《Copilot与自研管线_文档分割与Token对比.md》（Token 账的完整测算）、《确定性检索机制详解.md》、《AI代码生成提示词_原文版用.md》（P0–P4 日文提示词全集）。

> 一句话结论：**省 Token 的本质不是“压缩文档”，而是“每次生成时，只给这一次生成真正需要的那几段原文”。** 谁来切分决定成本和精度：脚本切分（0 Token、可审计）＞ 人工切分（0 Token、费工时、易漂移）＞ 让 LLM 自己切 / 自己找（最贵 + 会改字、漏行）。Copilot 本身没有确定性自动切分，所以最佳实践 = **人在 Copilot 外面先做好切分和组装，Copilot 只负责“在给定段落内写代码”这一件事。**

---

## 0. 前提：为什么在 Copilot 上“全盘输入”现在是真金白银的问题

1. **计费方式变了。** GitHub Copilot 已于 2026-06-01 改为按 Token 计费（AI Credits，input / output / cached 分别计量）。以前包月时“多挂几个文件”只是慢，现在是每一轮对话都按挂载量重复收费——对话越长，历史越累积，每一轮都在为前几轮挂过的全文再付一次钱。
2. **上下文不是仓库。** Copilot Chat / Agent 的上下文 = 系统提示 + 自定义指令 + **逐轮累积的对话历史** + 本轮 `#file` 附件 + Agent 工具输出。窗口满了会**自动摘要早期对话**：被压掉的设计书段落等于没给过，后面生成的代码就会“凭印象”补——这正是金融现场最不能接受的幻觉来源。
3. **注意力会被稀释。** 把 PL、BL、OW、定数一览全塞进同一个会话，BL 的处理会串进 Controller、别的方法的 Check 条件会串进当前方法。文档越全，串扰越严重——**“给得多”不等于“答得准”，在详细设计生成上恰恰相反。**

本案件的体量（实测）：

| 文档 | 字符数 | 内容 |
|---|---:|---|
| PL仕様書（Controller） | 16,336 | クラス定義 + 処理詳細 01–07 |
| BL仕様書（Service） | 15,438 | クラス定義 + 処理詳細 01–02，其中処理詳細02 单独 8,591 |
| OW定義シート（画面 DTO） | 5,584 | 字段定义 |
| OW定義シート DaoDto | 2,835 | DAO 用 DTO 定义 |
| 定数一覧（DUMMY 版，仅节选） | 11,085 | 约 100 行；**真实定数一覧是 2,000+ 行** |
| **合计（还不含真实定数全量、共通部品仕様書）** | **51,278** | 生成 15 个 Java 文件时若每次全量挂载，input 粗估约 **64 万 Token** |

对照：按阶段、按段落组装后生成同一批文件，input 粗估约 **7 万 Token**——约为全量方式的 **1/9**（测算口径见关联文档）。省下来的不只是钱，还有每一轮的响应速度和注意力。

## 策略 1：文档预处理——先把 Excel 变成“可按段取用”的 Markdown，再谈生成

### 原则

日本现场的试样书大多是 Excel：一册里混着表紙、改訂履歴、クラス定義、複数の処理詳細、画面遷移、コード表、備考。**Excel 原件不要直接拖给 Copilot**——合并单元格、跨页重复表头、脚注和版本号列会让模型读错行、读错列。预处理的目标不是“摘要”，而是**逐字转成 Markdown，并切成有坐标的段（section）**。

### 具体做法

1. **逐字转录，禁止摘要化。** 按 sheet 转成 Markdown 表格，行列数与原件一致，空单元格保留，合并单元格只在左上格写内容，读不清的地方标 `（判読困難）`，绝不让转录者（人或 AI）猜字。摘要一旦成为事实源，后面所有生成都在错的基础上进行，且无从审计。
2. **按结构边界切段，不按字数切段。** 切分单位 = sheet / 処理詳細番号 / 表格。一段 = 一个完整语义单位，例如 `BL.処理詳細02`、`BL.クラス定義.変数表`、`OW.項目定義.Select003DaoInDto`。固定字数 chunking 会把一张 Check 表从中间劈开，是精度事故的高发点。
3. **给每段建索引（人做一张表也行，脚本做更好）。** 每段记录：来源文件、标题路径、起止位置、一句话用途。生成时按索引取段，不靠记忆、不靠 Copilot 自己翻。
4. **明确划出“不是设计依据”的部分。** 表紙、改訂履歴、転录注记、作业メモ——这些段落要打标记，生成时**排除**。本案件实测踩过这个坑：転录注记子段混进 P2 的输入，等于让模型把“转录者的说明”当成设计内容，违反 grounding。排除规则必须包含子段，不只是父标题。
5. **重复表头只保留一份。** Excel 里每个処理詳細都重复一遍“画面ID / 画面名 / プログラムID / 作成者”表——预处理时标为共通表头，组装输入时只带一次。

### 效果

预处理是一次性投入（本案件 5 份文档共 88 张表，脚本校验行列数 0 处不一致）。做完之后，后面每一次生成都是“按索引取 2–5 段”，而不是“把整册书再搬一次”。

## 策略 2：分步 Prompt——按依赖顺序分阶段生成，一个会话只做一件事

### 原则

**永远不要在一个会话里说“请按这套设计书生成全部代码”。** 金融现场的程序是有依赖层级的，生成顺序必须服从依赖顺序，而且每个阶段单独开会话、单独验收。

### 标准分工（本 PoC 的 P0–P4）

| 阶段 | 做什么 | 输入只给 | 输出 |
|---|---|---|---|
| **P0 完备性门禁** | 生成前检查：跨文档表记不一致、引用了但未定义的部品 / 定数、处理内容与变数表的矛盾 | 全部文档的**索引 + 可疑段原文**（两阶段：先扫索引，再钻取可疑段） | 问题清单。**有 🔴 问题先回现场确认，不带病生成** |
| **P1 DTO** | 生成 DTO 类 | OW定義シート中**该 DTO 对应的段** | 一个 DTO 一个文件，逐个验收 |
| **P2 Controller（PL）** | 生成 Controller | PL 的クラス定義 + 対象処理詳細 + PL 変数表全量（変数表分散在各処理詳細里，必须全给，见下方案例） | Controller |
| **P3 Service（BL）** | 生成 Service | BL 的対象処理詳細 + クラス定義変数表 + 命中的定数行 + 命中的共通部品签名 | Service |
| **P4 DAO** | 生成 DAO 接口 / 呼出部 | BL 的**呼出仕様ブロック** + OW DaoDto 对应段 | DAO 接口 |

关键纪律：

- **一个 Chat = 一个方法（或一个 DTO）。** 生成完就关掉 / 新开会话。不要在同一会话里连续生成 7 个処理詳細——后半程的上下文里堆满了前几个方法的代码，串扰和摘要丢失都从这里来。
- **先让它复述，再让它写代码。** 对复杂方法，第一轮只要求输出“处理步骤 + Check 一览表”（不写 Java），人工对照设计书核对无误后，第二轮再写代码。复述轮的 Token 远小于“写错一整版代码再返工”。
- **手写顺序与生成顺序不同，不要混。** 人工手写是 DTO → DAO 接口 → Service → Controller（依赖顺序）；AI 的 P1–P4 编号是生成批次顺序。现场说明时要分清，否则作业者会拿错输入段。

## 策略 3：上下文控制——管好 Copilot 能“看见”的每一件东西

### 原则

Copilot 的上下文除了你挂的 `#file`，还包括打开的编辑器标签、对话历史、自定义指令。**你没管的部分，它都在读、都在计费、都可能串进生成结果。**

### 具体做法

1. **`#file` 只挂本轮的段，不挂整册。** 挂的是预处理后切好的段落文件 / 段落范围，而不是 `BL仕様書.md` 全文。判断标准：挂的每一段，你都能说出“这段对应要生成的哪几行代码”；说不出的段就不挂。
2. **`.github/copilot-instructions.md` 只放“项目规约”，不放“设计内容”。** 规约 = 命名规则、Getter/Setter 记法、注解格式、Java / Spring 版本、异常处理方针、TODO 的写法——这些每轮都需要、且总共几十行。设计内容（某个方法的处理流程）放进去等于每轮全员陪跑计费，还改不动。模板见附录 A。
3. **可复用的阶段指令做成 Prompt 文件，不要每次手打。** `.github/prompts/P0-check.prompt.md`、`P3-service.prompt.md` 等，把 grounding 规则固化在文件里（见策略 6 和附录 B），作业者只填“対象：BL.処理詳細02”一行。这既省 Token（不用每次粘贴长指令），也防止不同作业者写的指令口径漂移——金融现场レビュー时这是会被问的。
4. **关掉无关标签页，慎用 `#codebase`。** `#codebase` / Agent 模式让模型自己在仓库里找——找什么、找全没找全不可审计，工具输出还会累积进上下文反复计费。它适合“找类似实现参考”，**不适合做设计书的确定性检索**。设计书的段落必须由人 / 脚本按索引给，不能让它自己翻。
5. **长会话主动断舍离。** 一旦感觉回答开始引用“刚才那个方法”的逻辑，立即新开会话。新会话的成本（重挂 2–5 段）远低于长会话的累积计费 + 串扰返工。

## 策略 4：字典式部分参照——定数一览、共通部品、消息一览，只摘“用到的行”

### 原则

日本现场有三类“字典型”大文档：**定数一覧（本案件真实版 2,000+ 行）、共通部品仕様書、メッセージ一覧**。它们的共同特点是：某一个方法实际用到的只有几行到十几行。**整本挂载是全场最大的 Token 浪费，没有之一。**

### 具体做法

1. **先 grep，后挂载。** 生成前先在字典里精确检索本次处理内容里出现的名字（定数名、部品名、メッセージID），只把命中的行摘成一个小表挂给 Copilot。本案件的实测：P3 组装时先统计 BL 里出现的定数——结果发现 BL 的处理内容是用**描述性文字**引用定数的（如“検索画面遷移区分に定数、ブランクを設定”），86 个候选定数名一个都没直接出现。
2. **检索不到 = TODO，绝不猜值。** 上面这种情况在日本现场极其常见：设计书写了“定数、○○を設定”但没写定数物理名 / 值。正确动作是在代码里留 `// TODO: 設計確認 — 定数名・値が設計書に明記されていない` 并登记到待确认清单，**而不是让 Copilot 编一个看起来合理的常量名**。它编得越像，レビュー越难发现，上线风险越大。
3. **共通部品只给签名，不给仕様書全文。** Copilot 需要的是“类名 + 方法签名 + 引数 / 戻り値”三行，不是部品的内部处理流程。例如本案件追踪过的一条链：

```text
PL.処理内容「変数.WebDTO初期化部品.initWebDto(...)」
→ PL.変数表「WebDTO初期化部品 → JOAKKBDtoUtil」
→ 需要的输入只有：JOAKKBDtoUtil.initWebDto のシグネチャ 1 件
```

签名还没拿到（共通部品仕様書未收集）时，就标 TODO，不要让 Copilot 按方法名猜参数。
4. **摘录表要带出处。** 每行摘录注明“定数一覧 第○行 / 部品仕様書 ○章”。生成代码的注释和変換ログ里能溯源，现场レビューで「この定数の根拠は？」と闻かれたときに即答できる。

## 策略 5：Check 处理专项——先抽“チェック一覧表”，再生成代码

### 原则

详细设计里 Token 密度最高、最容易丢的不是主流程，而是 **Check 处理**：単項目チェック（必須、桁数、形式、コード値）、相関チェック（A と B の組み合わせ）、存在チェック（マスタ / 端末構成情報の有無）、権限・状態チェック。它们通常以嵌套编号（`3-6-2-1` 这种四层编号）散在处理内容表里，**全量投喂时模型最先丢的就是这些深层分支**——主流程看起来对，一测才发现少了一半 Check，这在金融现场是致命的（Check 漏れ = そのまま本番障害候補）。

### 具体做法

1. **Check 单独成表，作为生成的中间产物。** 先用一个独立 Prompt（只给対象処理詳細）让 Copilot 抽出チェック一覧：`チェックID / 対象項目 / 条件 / NG時の処理（メッセージID、例外、遷移先）/ 設計書の番号`。这张表人工对照设计书逐行核（核对成本：一张表 vs 一整版代码，便宜得多）。
2. **核对通过后，把这张表 + 原处理段一起给代码生成轮。** 并明确指令：“チェック一覧の全行を実装すること。実装できない行は TODO にすること。一覧に無いチェックを足さないこと。”
3. **NG 时处理必须带消息 ID 原文。** 如 `JOCOMNG0165E` 这类メッセージID DEnum、定数名，必须从设计书逐字复制到 Check 表里，不许 Copilot 改写。消息 ID 写错一位，运行时就是另一条消息。
4. **桁数・形式チェックは「条件の原文」を残す。** 例：“半角2桁以外の場合”——不要在摘录时改写成“length!= 2”，原文的“半角”二字决定了要不要做全角→半角的判定，改写就丢信息。

## 策略 6：Grounding 与生成后校验——省 Token 不能以“它编得像”为代价

### 原则

上面五条都在“少给”，这一条保证“少给不等于少对”。金融现场的铁律：**生成代码只能使用输入段落里明确记载的内容；缺失 / 含糊一律 TODO + 设计确认，严禁推断。**

### 固化到每个 Prompt 里的规则（日文原文，附录 B 有完整版）

```text
- 設計書に明記されていない定数名・値、メソッドシグネチャ、フィールド名は推測しないこと。TODOコメントとして残し、理由を書くこと。
- 転記メモ・転录注记は設計の根拠ではない。使用しないこと。
- 判読困難とマークされた箇所は TODO とすること。
- 入力として渡されたセクション以外の処理・チェックを追加しないこと。
```

### 生成后三道校验（缺一不可）

| 校验 | 做什么 | 抓什么问题 |
|---|---|---|
| **コンパイル校验** | `javac` / Maven 编译生成代码 | 签名猜错、类型不存在、import 缺失 |
| **Grounding 白名单校验** | 脚本 grep 生成代码里的定数名、部品名、メッセージID、DTO 字段名，逐一回查是否在输入段里出现过 | 幻觉出来的常量、字段、方法 |
| **TODO 清单化** | 把所有 TODO 抽成一张表，逐项登记去向（现场确认 / 次期设计书 / 部品仕様書待ち） | TODO 被默默吞掉、无人跟进 |

修复要有界：自动 / 半自动修复最多 3 轮，3 轮不过就停下来报给人，不要让 Copilot 在长会话里无限改——每改一轮都在烧 Token，且越改越偏离设计书原文。

---

## 策略 7：Token 运营——把消耗变成可汇报的数字

金融现场的 PoC 最后都要汇报“AI 生成的成本和效果”。从第一天就养成三个习惯，汇报时不用临时编数字：

1. **按阶段记账。** 每次生成记录：阶段（P1–P4）、挂了哪几段（字符数）、生成文件、修复轮数。这就是変換ログ，顺带满足审计要求。
2. **用实测对比说话。** 本案件的汇报口径已经成立：“全量挂载约 64 万 input Token vs 分段组装约 7 万，约 1/9；且全量方式出现过 BL 处理串入 Controller 的风险，分段方式未出现。”
3. **不把 Prompt 缓存当预算前提。** Copilot / API 的缓存能让重复上下文便宜一些，但命中不受你控制、上下文被自动摘要后也会失效。预算按“无缓存”估，省下的算惊喜。

# 核心案例：一个带大量 Check 的详细设计，怎么喂才对

## 案例背景

対象：`JOJAMPG01W010Service.doNoAction`（外部診断）、BL仕様書 処理詳細02。

这一段为什么难：

- 体量大：单独一段 **8,591 字符**，是 BL 全册的 56%。
- 结构深：処理内容编号到四层（`3-6-5-1-1-1`），含 変数 10 项、DAO 呼出 3 件（select001 / 002 / 003）。
- Check 密集（节选）：

| 设计书编号 | Check 内容（原文要旨） | NG 时 / 判定结果 |
|---|---|---|
| 3-5 | DAO取得001 の件数 = 定数「検索結果件数 0件」か | メッセージID `JOCOMNG0165E`（システムエラー）を設定し、例外をスロー |
| 3-6-2 | 県番号の桁数チェック：半角2桁以外か | 組合合併チェックフラグ = true |
| 3-6-3 | 組合番号の桁数チェック：半角3桁以外か | 同上 |
| 3-6-4 | 支所番号の桁数チェック：半角2桁以外か | 同上 |
| 3-6-5-1 | 入力組合区分 = 全国本部 の場合：県番号が `"48"` か | 一致 → サービスOutDTO に分類コード「全国本部」を設定；不一致 → フラグ = true |
| 3-6-5-2 | 入力組合区分 = 県本部 の場合：県番号が `"01"～"47"` か | 一致 → 分類コード「県本部」を設定；不一致 → フラグ = true |

- 还有坑：処理内容里多处只写“定数、○○を設定”而**没写定数物理名和值**；`アプリ共通エリア` 被用了 8 次却没有変数表宣言、类名未定。这些都不是“让 AI 猜”的地方，是 TODO / 设计确认事项。

## ❌ 错误 / 浪费 Token 的输入方式

```text

把 PL仕様書、BL仕様書、OW定義シート×2、定数一覧（全2,000+行）、
共通部品仕様書 全部 #file 挂进同一个 Chat，标签页里还开着别的画面代码。


この設計書一式に基づいて、JOJAMPG01W010 の Controller と Service の
全コードを生成してください。定数が不明な場合は一般的な値で補ってください。
```

会发生什么（全部是本类项目实测 / 可预见的事故）：

| # | 后果 | 原因 |
|---|---|---|
| 1 | **Token 爆炸**：这一轮 input 就是 5 万字符 + 定数全量（真实定数一覧单册就远超本案其余文档之和）；之后在同一会话里每问一句，都重复计费全量 | 全量挂载 × 对话累积 |
| 2 | **Check 漏実装**：`3-6-2～3-6-4` 的桁数チェック只实现 1–2 个，`3-6-5` 的 `"48"` / `"01"～"47"` 判定被合并成一句注释 | 深层嵌套分支在长上下文里最先被注意力丢弃 |
| 3 | **定数捏造**：“一般的な値で補って”等于授权幻觉——它会编出形似的定数名和值，混在真代码里，レビューで見抜きにくい | 指令与 grounding 铁律正面冲突 |
| 4 | **跨层串扰**：Service 的処理に Controller（PL）の画面遷移ロジックが混入 | PL / BL 同会话共存 |
| 5 | **中途被摘要**：生成到第二个类时窗口触发自动摘要，前半的设计段被压掉，后半代码开始“凭印象”写，但表面上仍然流畅 | 长会话 + 大附件 |

这一版代码看起来“完成度很高”，实际上 Check 覆盖率、定数正确性都不可信——**返工成本（逐行对照设计书复核整版代码）远高于分步生成的成本，Token 也并没有省。**

## ✅ 正确 / 节省 Token 的输入方式（四步）

### 第 0 步：P0 门禁（只扫，不写代码）

```text
挂载：BL.クラス定義 + BL.処理詳細02（原文段，约 9,800 字符）
Prompt（.github/prompts/P0-check.prompt.md）：
設計書の不整合・未定義参照を洗い出してください。コードは生成しないこと。
特に：変数表に宣言のないエリア参照、定数名が明記されていない箇所、
呼出仕様はあるが DTO 定義が別紙にある箇所を番号付きで列挙すること。
```

产出先行确认：`アプリ共通エリア` 无宣言 → 设计确认；定数物理名缺失数件 → TODO 预定。**带着已知问题清单进生成，比生成完再发现问题便宜一个数量级。**

### 第 1 步：DTO 先行（P1 / P4 的输入）

```text
挂载：OW定義シート DaoDto 中 Select001 / 002 / 003 对应的 3 段（约 1,500 字符）
+ BL.処理詳細02 的呼出仕様ブロック 3 件
生成：JOJAMPG01Select001DaoInDto / OutDto、002、003 共 6 个类，逐个验收
```

DTO 是后面 Service 的“型纸”。先把 DTO 定死，Service 生成时只需引用类名，不用再挂 OW 全文。

### 第 2 步：抽チェック一覧表（只抽，不写 Java）

```text
挂载：BL.処理詳細02 原文段（8,591 字符）
Prompt：
処理詳細02 からチェック処理だけを抽出し、一覧表にしてください。
列：番号 / 対象項目 / 条件（原文のまま） / NG時の処理 / メッセージID・定数（原文のまま）
コードは書かないこと。一覧に無いチェックを補わないこと。
条件に定数名が明記されていない場合は「定数名未記載」と書くこと。
```

人工核对这张表（对照设计书约 15 分钟），确认 `3-6-2 / 3-6-3 / 3-6-4` 三件桁数チェック、`3-6-5-1 "48"`、`3-6-5-2 "01"～"47"`、`3-5 JOCOMNG0165E` 全部在表、条件原文无改写。

### 第 3 步：只生成 doNoAction 一个方法（P3）

```text
挂载（合计约 13,000 字符，约为全量方式的 1/4，且每段都用得上）：
- BL.クラス定義.変数表（aina / uina / messageBundle / DAO、约 600 字符）
- BL.処理詳細02 原文段（8,591 字符）
- 第 2 步核对通过的チェック一覧表（约 1,500 字符）
- 定数摘录表：本次 grep 命中的定数行のみ（命中 0 件の項目は TODO 指示として明記）
- 共通部品签名摘录：uina / aina / messageBundle の使用メソッドのみ
（シグネチャ未入手の部品は「TODO：部品仕様書待ち」と指示）

Prompt（.github/prompts/P3-service.prompt.md）：
JOJAMPG01W010Service.doNoAction だけを生成してください。
- チェック一覧表の全行を実装すること。追加のチェックを足さないこと。
- 定数名・値が設計書に明記されていない箇所は TODOコメントにすること（推測禁止）。
- DAO呼出は呼出仕様ブロックの通りにし、DTO は生成済みクラスを参照すること。
- 生成後に、処理内容の番号とコードの対応を自己申告リストとして添えること。
```

生成后执行策略 6 的三道校验：编译 → 白名单 grep（定数名 / メッセージID / 字段名逐一回查输入段）→ TODO 抽表登记。

### 两方式对比

| 观 点 | ❌ 全量一括 | ✅ 分步（本节） |
|---|---|---|
| 单会话 input | 5 万字符 + 定数全量 2,000+ 行 | 每步 1,500–13,000 字符 |
| 生成 15 文件的 input 粗估 | 约 64 万 Token | 约 7 万 Token（约 1/9） |
| Check 覆盖 | 靠模型注意力，漏了不知道漏了什么 | チェック一覧表で先に固定，逐行核对可能 |
| 定数不明时 | 被指令授权“补一般值”→ 捏造 | TODO + 设计确认，问题显性化 |
| 出错定位 | 整版代码逐行复核 | 定位到某一步、某一段、某一张表 |
| 审计 / 汇报 | 说不清哪段设计生出了哪行代码 | 変換ログ：段 → Prompt → 代码，一一对应 |

# 附录 C：与自研管线是什么关系

本手册解决的是“**现场工具已经是 Copilot** 时，怎么用得省、用得准”。
如果 PoC 要验证的是自动化与可审计性本身，最省 Token 的形态仍是混合式：**切分和组装用本地脚本做（确定性、0 Token、有変換ログ），只把最后一步的生成调用交给 Copilot**——而不是让 Copilot 自己切、自己找。测算对比见《Copilot与自研管线_文档分割与Token对比.md》。
