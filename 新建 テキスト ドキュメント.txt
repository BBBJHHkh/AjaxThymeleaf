# Copilot 试样书过长时：Token 节约与精度提升最佳实践

作成：2026-10-09
定位：面向日本大型金融 IT 现场（证券 / 银行 / 保险 / JA・共济类严谨项目）的实战手册。不是 Copilot 功能介绍，而是回答一个具体问题——**试样书（仕様書）又长又多时，怎么喂给 GitHub Copilot 才能既省 Token、又不丢细节、不产生幻觉。**
案例：全部以本 PoC 的真实案件 `JOJAMPG01W010`（JA向けマイページメニュー、PL / BL 详细设计）为例，数字均为实测，不是示意数字。
关联文档：《Copilot与自研管线_文档分割与Token对比.md》（Token 账的完整测算）、《确定性检索机制详解.md》、《AI代码生成提示词_原文版用.md》（P0–P4 日文提示词全集）。

> 一句话结论：**省 Token 的本质不是“压缩文档”，而是“每次生成时，只给这一次生成真正需要的那几段原文”。** 谁来切分决定成本和精度：脚本切分（0 Token、可审计）＞ 人工切分（0 Token、费工时、易漂移）＞ 让 LLM 自己切 / 自己找（最贵 + 会改字、漏行）。Copilot 本身没有确定性自动切分，所以最佳实践 = **人在 Copilot 外面先做好切分和组装，Copilot 只负责“在给定段落内写代码”这一件事。**

---

## 0. 前提：为什么在 Copilot 上“全盘输入”现在是真金白银的问题

1. **计费方式变了。** GitHub Copilot 已于 2026-06-01 改为按 Token 计费（AI Credits，input / output / cached 分别计量）。以前包月时“多挂几个文件”只是慢，现在是每一轮对话都按挂载量重复收费——对话越长，历史越累积，每一轮都在为前几轮挂过的全文再付一次钱。
2. **上下文不是仓库。** Copilot Chat / Agent 的上下文 = 系统提示 + 自定义指令 + **逐轮累积的对话历史** + 本轮 `#file` 附件 + Agent 工具输出。窗口满了会**自动摘要早期对话**：被压掉的设计书段落等于没给过，后面生成的代码就会“凭印象”补——这正是金融现场最不能接受的幻觉来源。
3. **注意力会被稀释。** 把 PL、BL、OW、定数一览全塞进同一个会话，BL 的处理会串进 Controller、别的方法的 Check 条件会串进当前方法。文档越全，串扰越严重——**“给得多”不等于“答得准”，在详细设计生成上恰恰相反。**

本案件的体量（实测）：

| 文档 | 字符数 | 内容 |
|---|---:|---|
| PL仕様書（Controller） | 16,336 | クラス定義 + 処理詳細 01–07 |
| BL仕様書（Service） | 15,438 | クラス定義 + 処理詳細 01–02，其中処理詳細02 单独 8,591 |
| OW定義シート（画面 DTO） | 5,584 | 字段定义 |
| OW定義シート DaoDto | 2,835 | DAO 用 DTO 定义 |
| 定数一覧（DUMMY 版，仅节选） | 11,085 | 约 100 行；**真实定数一覧是 2,000+ 行** |
| **合计（还不含真实定数全量、共通部品仕様書）** | **51,278** | 生成 15 个 Java 文件时若每次全量挂载，input 粗估约 **64 万 Token** |

对照：按阶段、按段落组装后生成同一批文件，input 粗估约 **7 万 Token**——约为全量方式的 **1/9**（测算口径见关联文档）。省下来的不只是钱，还有每一轮的响应速度和注意力。

## 策略 1：文档预处理——先把 Excel 变成“可按段取用”的 Markdown，再谈生成

### 原则

日本现场的试样书大多是 Excel：一册里混着表紙、改訂履歴、クラス定義、複数の処理詳細、画面遷移、コード表、備考。**Excel 原件不要直接拖给 Copilot**——合并单元格、跨页重复表头、脚注和版本号列会让模型读错行、读错列。预处理的目标不是“摘要”，而是**逐字转成 Markdown，并切成有坐标的段（section）**。

### 具体做法

1. **逐字转录，禁止摘要化。** 按 sheet 转成 Markdown 表格，行列数与原件一致，空单元格保留，合并单元格只在左上格写内容，读不清的地方标 `（判読困難）`，绝不让转录者（人或 AI）猜字。摘要一旦成为事实源，后面所有生成都在错的基础上进行，且无从审计。
2. **按结构边界切段，不按字数切段。** 切分单位 = sheet / 処理詳細番号 / 表格。一段 = 一个完整语义单位，例如 `BL.処理詳細02`、`BL.クラス定義.変数表`、`OW.項目定義.Select003DaoInDto`。固定字数 chunking 会把一张 Check 表从中间劈开，是精度事故的高发点。
3. **给每段建索引（人做一张表也行，脚本做更好）。** 每段记录：来源文件、标题路径、起止位置、一句话用途。生成时按索引取段，不靠记忆、不靠 Copilot 自己翻。
4. **明确划出“不是设计依据”的部分。** 表紙、改訂履歴、転录注记、作业メモ——这些段落要打标记，生成时**排除**。本案件实测踩过这个坑：転录注记子段混进 P2 的输入，等于让模型把“转录者的说明”当成设计内容，违反 grounding。排除规则必须包含子段，不只是父标题。
5. **重复表头只保留一份。** Excel 里每个処理詳細都重复一遍“画面ID / 画面名 / プログラムID / 作成者”表——预处理时标为共通表头，组装输入时只带一次。

### 效果

预处理是一次性投入（本案件 5 份文档共 88 张表，脚本校验行列数 0 处不一致）。做完之后，后面每一次生成都是“按索引取 2–5 段”，而不是“把整册书再搬一次”。

## 策略 2：分步 Prompt——按依赖顺序分阶段生成，一个会话只做一件事

### 原则

**永远不要在一个会话里说“请按这套设计书生成全部代码”。** 金融现场的程序是有依赖层级的，生成顺序必须服从依赖顺序，而且每个阶段单独开会话、单独验收。

### 标准分工（本 PoC 的 P0–P4）

| 阶段 | 做什么 | 输入只给 | 输出 |
|---|---|---|---|
| **P0 完备性门禁** | 生成前检查：跨文档表记不一致、引用了但未定义的部品 / 定数、处理内容与变数表的矛盾 | 全部文档的**索引 + 可疑段原文**（两阶段：先扫索引，再钻取可疑段） | 问题清单。**有 🔴 问题先回现场确认，不带病生成** |
| **P1 DTO** | 生成 DTO 类 | OW定義シート中**该 DTO 对应的段** | 一个 DTO 一个文件，逐个验收 |
| **P2 Controller（PL）** | 生成 Controller | PL 的クラス定義 + 対象処理詳細 + PL 変数表全量（変数表分散在各処理詳細里，必须全给，见下方案例） | Controller |
| **P3 Service（BL）** | 生成 Service | BL 的対象処理詳細 + クラス定義変数表 + 命中的定数行 + 命中的共通部品签名 | Service |
| **P4 DAO** | 生成 DAO 接口 / 呼出部 | BL 的**呼出仕様ブロック** + OW DaoDto 对应段 | DAO 接口 |

关键纪律：

- **一个 Chat = 一个方法（或一个 DTO）。** 生成完就关掉 / 新开会话。不要在同一会话里连续生成 7 个処理詳細——后半程的上下文里堆满了前几个方法的代码，串扰和摘要丢失都从这里来。
- **先让它复述，再让它写代码。** 对复杂方法，第一轮只要求输出“处理步骤 + Check 一览表”（不写 Java），人工对照设计书核对无误后，第二轮再写代码。复述轮的 Token 远小于“写错一整版代码再返工”。
- **手写顺序与生成顺序不同，不要混。** 人工手写是 DTO → DAO 接口 → Service → Controller（依赖顺序）；AI 的 P1–P4 编号是生成批次顺序。现场说明时要分清，否则作业者会拿错输入段。

## 策略 3：上下文控制——管好 Copilot 能“看见”的每一件东西

### 原则

Copilot 的上下文除了你挂的 `#file`，还包括打开的编辑器标签、对话历史、自定义指令。**你没管的部分，它都在读、都在计费、都可能串进生成结果。**

### 具体做法

1. **`#file` 只挂本轮的段，不挂整册。** 挂的是预处理后切好的段落文件 / 段落范围，而不是 `BL仕様書.md` 全文。判断标准：挂的每一段，你都能说出“这段对应要生成的哪几行代码”；说不出的段就不挂。
2. **`.github/copilot-instructions.md` 只放“项目规约”，不放“设计内容”。** 规约 = 命名规则、Getter/Setter 记法、注解格式、Java / Spring 版本、异常处理方针、TODO 的写法——这些每轮都需要、且总共几十行。设计内容（某个方法的处理流程）放进去等于每轮全员陪跑计费，还改不动。模板见附录 A。
3. **可复用的阶段指令做成 Prompt 文件，不要每次手打。** `.github/prompts/P0-check.prompt.md`、`P3-service.prompt.md` 等，把 grounding 规则固化在文件里（见策略 6 和附录 B），作业者只填“対象：BL.処理詳細02”一行。这既省 Token（不用每次粘贴长指令），也防止不同作业者写的指令口径漂移——金融现场レビュー时这是会被问的。
4. **关掉无关标签页，慎用 `#codebase`。** `#codebase` / Agent 模式让模型自己在仓库里找——找什么、找全没找全不可审计，工具输出还会累积进上下文反复计费。它适合“找类似实现参考”，**不适合做设计书的确定性检索**。设计书的段落必须由人 / 脚本按索引给，不能让它自己翻。
5. **长会话主动断舍离。** 一旦感觉回答开始引用“刚才那个方法”的逻辑，立即新开会话。新会话的成本（重挂 2–5 段）远低于长会话的累积计费 + 串扰返工。

## 策略 4：字典式部分参照——定数一览、共通部品、消息一览，只摘“用到的行”

### 原则

日本现场有三类“字典型”大文档：**定数一覧（本案件真实版 2,000+ 行）、共通部品仕様書、メッセージ一覧**。它们的共同特点是：某一个方法实际用到的只有几行到十几行。**整本挂载是全场最大的 Token 浪费，没有之一。**

### 具体做法

1. **先 grep，后挂载。** 生成前先在字典里精确检索本次处理内容里出现的名字（定数名、部品名、メッセージID），只把命中的行摘成一个小表挂给 Copilot。本案件的实测：P3 组装时先统计 BL 里出现的定数——结果发现 BL 的处理内容是用**描述性文字**引用定数的（如“検索画面遷移区分に定数、ブランクを設定”），86 个候选定数名一个都没直接出现。
2. **检索不到 = TODO，绝不猜值。** 上面这种情况在日本现场极其常见：设计书写了“定数、○○を設定”但没写定数物理名 / 值。正确动作是在代码里留 `// TODO: 設計確認 — 定数名・値が設計書に明記されていない` 并登记到待确认清单，**而不是让 Copilot 编一个看起来合理的常量名**。它编得越像，レビュー越难发现，上线风险越大。
3. **共通部品只给签名，不给仕様書全文。** Copilot 需要的是“类名 + 方法签名 + 引数 / 戻り値”三行，不是部品的内部处理流程。例如本案件追踪过的一条链：

```text
PL.処理内容「変数.WebDTO初期化部品.initWebDto(...)」
→ PL.変数表「WebDTO初期化部品 → JOAKKBDtoUtil」
→ 需要的输入只有：JOAKKBDtoUtil.initWebDto のシグネチャ 1 件
```

签名还没拿到（共通部品仕様書未收集）时，就标 TODO，不要让 Copilot 按方法名猜参数。
4. **摘录表要带出处。** 每行摘录注明“定数一覧 第○行 / 部品仕様書 ○章”。生成代码的注释和変換ログ里能溯源，现场レビューで「この定数の根拠は？」と闻かれたときに即答できる。

## 策略 5：Check 处理专项——先抽“チェック一覧表”，再生成代码

### 原则

详细设计里 Token 密度最高、最容易丢的不是主流程，而是 **Check 处理**：単項目チェック（必須、桁数、形式、コード値）、相関チェック（A と B の組み合わせ）、存在チェック（マスタ / 端末構成情報の有無）、権限・状態チェック。它们通常以嵌套编号（`3-6-2-1` 这种四层编号）散在处理内容表里，**全量投喂时模型最先丢的就是这些深层分支**——主流程看起来对，一测才发现少了一半 Check，这在金融现场是致命的（Check 漏れ = そのまま本番障害候補）。

### 具体做法

1. **Check 单独成表，作为生成的中间产物。** 先用一个独立 Prompt（只给対象処理詳細）让 Copilot 抽出チェック一覧：`チェックID / 対象項目 / 条件 / NG時の処理（メッセージID、例外、遷移先）/ 設計書の番号`。这张表人工对照设计书逐行核（核对成本：一张表 vs 一整版代码，便宜得多）。
2. **核对通过后，把这张表 + 原处理段一起给代码生成轮。** 并明确指令：“チェック一覧の全行を実装すること。実装できない行は TODO にすること。一覧に無いチェックを足さないこと。”
3. **NG 时处理必须带消息 ID 原文。** 如 `JOCOMNG0165E` 这类メッセージID DEnum、定数名，必须从设计书逐字复制到 Check 表里，不许 Copilot 改写。消息 ID 写错一位，运行时就是另一条消息。
4. **桁数・形式チェックは「条件の原文」を残す。** 例：“半角2桁以外の場合”——不要在摘录时改写成“length!= 2”，原文的“半角”二字决定了要不要做全角→半角的判定，改写就丢信息。

## 策略 6：Grounding 与生成后校验——省 Token 不能以“它编得像”为代价

### 原则

上面五条都在“少给”，这一条保证“少给不等于少对”。金融现场的铁律：**生成代码只能使用输入段落里明确记载的内容；缺失 / 含糊一律 TODO + 设计确认，严禁推断。**

### 固化到每个 Prompt 里的规则（日文原文，附录 B 有完整版）

```text
- 設計書に明記されていない定数名・値、メソッドシグネチャ、フィールド名は推測しないこと。TODOコメントとして残し、理由を書くこと。
- 転記メモ・転录注记は設計の根拠ではない。使用しないこと。
- 判読困難とマークされた箇所は TODO とすること。
- 入力として渡されたセクション以外の処理・チェックを追加しないこと。
```

### 生成后三道校验（缺一不可）

| 校验 | 做什么 | 抓什么问题 |
|---|---|---|
| **コンパイル校验** | `javac` / Maven 编译生成代码 | 签名猜错、类型不存在、import 缺失 |
| **Grounding 白名单校验** | 脚本 grep 生成代码里的定数名、部品名、メッセージID、DTO 字段名，逐一回查是否在输入段里出现过 | 幻觉出来的常量、字段、方法 |
| **TODO 清单化** | 把所有 TODO 抽成一张表，逐项登记去向（现场确认 / 次期设计书 / 部品仕様書待ち） | TODO 被默默吞掉、无人跟进 |

修复要有界：自动 / 半自动修复最多 3 轮，3 轮不过就停下来报给人，不要让 Copilot 在长会话里无限改——每改一轮都在烧 Token，且越改越偏离设计书原文。

---

## 策略 7：Token 运营——把消耗变成可汇报的数字

金融现场的 PoC 最后都要汇报“AI 生成的成本和效果”。从第一天就养成三个习惯，汇报时不用临时编数字：

1. **按阶段记账。** 每次生成记录：阶段（P1–P4）、挂了哪几段（字符数）、生成文件、修复轮数。这就是変換ログ，顺带满足审计要求。
2. **用实测对比说话。** 本案件的汇报口径已经成立：“全量挂载约 64 万 input Token vs 分段组装约 7 万，约 1/9；且全量方式出现过 BL 处理串入 Controller 的风险，分段方式未出现。”
3. **不把 Prompt 缓存当预算前提。** Copilot / API 的缓存能让重复上下文便宜一些，但命中不受你控制、上下文被自动摘要后也会失效。预算按“无缓存”估，省下的算惊喜。

# 核心案例：一个带大量 Check 的详细设计，怎么喂才对

## 案例背景

対象：`JOJAMPG01W010Service.doNoAction`（外部診断）、BL仕様書 処理詳細02。

这一段为什么难：

- 体量大：单独一段 **8,591 字符**，是 BL 全册的 56%。
- 结构深：処理内容编号到四层（`3-6-5-1-1-1`），含 変数 10 项、DAO 呼出 3 件（select001 / 002 / 003）。
- Check 密集（节选）：

| 设计书编号 | Check 内容（原文要旨） | NG 时 / 判定结果 |
|---|---|---|
| 3-5 | DAO取得001 の件数 = 定数「検索結果件数 0件」か | メッセージID `JOCOMNG0165E`（システムエラー）を設定し、例外をスロー |
| 3-6-2 | 県番号の桁数チェック：半角2桁以外か | 組合合併チェックフラグ = true |
| 3-6-3 | 組合番号の桁数チェック：半角3桁以外か | 同上 |
| 3-6-4 | 支所番号の桁数チェック：半角2桁以外か | 同上 |
| 3-6-5-1 | 入力組合区分 = 全国本部 の場合：県番号が `"48"` か | 一致 → サービスOutDTO に分類コード「全国本部」を設定；不一致 → フラグ = true |
| 3-6-5-2 | 入力組合区分 = 県本部 の場合：県番号が `"01"～"47"` か | 一致 → 分類コード「県本部」を設定；不一致 → フラグ = true |

- 还有坑：処理内容里多处只写“定数、○○を設定”而**没写定数物理名和值**；`アプリ共通エリア` 被用了 8 次却没有変数表宣言、类名未定。这些都不是“让 AI 猜”的地方，是 TODO / 设计确认事项。

## ❌ 错误 / 浪费 Token 的输入方式

```text

把 PL仕様書、BL仕様書、OW定義シート×2、定数一覧（全2,000+行）、
共通部品仕様書 全部 #file 挂进同一个 Chat，标签页里还开着别的画面代码。


この設計書一式に基づいて、JOJAMPG01W010 の Controller と Service の
全コードを生成してください。定数が不明な場合は一般的な値で補ってください。
```

会发生什么（全部是本类项目实测 / 可预见的事故）：

| # | 后果 | 原因 |
|---|---|---|
| 1 | **Token 爆炸**：这一轮 input 就是 5 万字符 + 定数全量（真实定数一覧单册就远超本案其余文档之和）；之后在同一会话里每问一句，都重复计费全量 | 全量挂载 × 对话累积 |
| 2 | **Check 漏実装**：`3-6-2～3-6-4` 的桁数チェック只实现 1–2 个，`3-6-5` 的 `"48"` / `"01"～"47"` 判定被合并成一句注释 | 深层嵌套分支在长上下文里最先被注意力丢弃 |
| 3 | **定数捏造**：“一般的な値で補って”等于授权幻觉——它会编出形似的定数名和值，混在真代码里，レビューで見抜きにくい | 指令与 grounding 铁律正面冲突 |
| 4 | **跨层串扰**：Service 的処理に Controller（PL）の画面遷移ロジックが混入 | PL / BL 同会话共存 |
| 5 | **中途被摘要**：生成到第二个类时窗口触发自动摘要，前半的设计段被压掉，后半代码开始“凭印象”写，但表面上仍然流畅 | 长会话 + 大附件 |

这一版代码看起来“完成度很高”，实际上 Check 覆盖率、定数正确性都不可信——**返工成本（逐行对照设计书复核整版代码）远高于分步生成的成本，Token 也并没有省。**

## ✅ 正确 / 节省 Token 的输入方式（四步）

### 第 0 步：P0 门禁（只扫，不写代码）

```text
挂载：BL.クラス定義 + BL.処理詳細02（原文段，约 9,800 字符）
Prompt（.github/prompts/P0-check.prompt.md）：
設計書の不整合・未定義参照を洗い出してください。コードは生成しないこと。
特に：変数表に宣言のないエリア参照、定数名が明記されていない箇所、
呼出仕様はあるが DTO 定義が別紙にある箇所を番号付きで列挙すること。
```

产出先行确认：`アプリ共通エリア` 无宣言 → 设计确认；定数物理名缺失数件 → TODO 预定。**带着已知问题清单进生成，比生成完再发现问题便宜一个数量级。**

### 第 1 步：DTO 先行（P1 / P4 的输入）

```text
挂载：OW定義シート DaoDto 中 Select001 / 002 / 003 对应的 3 段（约 1,500 字符）
+ BL.処理詳細02 的呼出仕様ブロック 3 件
生成：JOJAMPG01Select001DaoInDto / OutDto、002、003 共 6 个类，逐个验收
```

DTO 是后面 Service 的“型纸”。先把 DTO 定死，Service 生成时只需引用类名，不用再挂 OW 全文。

### 第 2 步：抽チェック一覧表（只抽，不写 Java）

```text
挂载：BL.処理詳細02 原文段（8,591 字符）
Prompt：
処理詳細02 からチェック処理だけを抽出し、一覧表にしてください。
列：番号 / 対象項目 / 条件（原文のまま） / NG時の処理 / メッセージID・定数（原文のまま）
コードは書かないこと。一覧に無いチェックを補わないこと。
条件に定数名が明記されていない場合は「定数名未記載」と書くこと。
```

人工核对这张表（对照设计书约 15 分钟），确认 `3-6-2 / 3-6-3 / 3-6-4` 三件桁数チェック、`3-6-5-1 "48"`、`3-6-5-2 "01"～"47"`、`3-5 JOCOMNG0165E` 全部在表、条件原文无改写。

### 第 3 步：只生成 doNoAction 一个方法（P3）

```text
挂载（合计约 13,000 字符，约为全量方式的 1/4，且每段都用得上）：
- BL.クラス定義.変数表（aina / uina / messageBundle / DAO、约 600 字符）
- BL.処理詳細02 原文段（8,591 字符）
- 第 2 步核对通过的チェック一覧表（约 1,500 字符）
- 定数摘录表：本次 grep 命中的定数行のみ（命中 0 件の項目は TODO 指示として明記）
- 共通部品签名摘录：uina / aina / messageBundle の使用メソッドのみ
（シグネチャ未入手の部品は「TODO：部品仕様書待ち」と指示）

Prompt（.github/prompts/P3-service.prompt.md）：
JOJAMPG01W010Service.doNoAction だけを生成してください。
- チェック一覧表の全行を実装すること。追加のチェックを足さないこと。
- 定数名・値が設計書に明記されていない箇所は TODOコメントにすること（推測禁止）。
- DAO呼出は呼出仕様ブロックの通りにし、DTO は生成済みクラスを参照すること。
- 生成後に、処理内容の番号とコードの対応を自己申告リストとして添えること。
```

生成后执行策略 6 的三道校验：编译 → 白名单 grep（定数名 / メッセージID / 字段名逐一回查输入段）→ TODO 抽表登记。

### 两方式对比

| 观 点 | ❌ 全量一括 | ✅ 分步（本节） |
|---|---|---|
| 单会话 input | 5 万字符 + 定数全量 2,000+ 行 | 每步 1,500–13,000 字符 |
| 生成 15 文件的 input 粗估 | 约 64 万 Token | 约 7 万 Token（约 1/9） |
| Check 覆盖 | 靠模型注意力，漏了不知道漏了什么 | チェック一覧表で先に固定，逐行核对可能 |
| 定数不明时 | 被指令授权“补一般值”→ 捏造 | TODO + 设计确认，问题显性化 |
| 出错定位 | 整版代码逐行复核 | 定位到某一步、某一段、某一张表 |
| 审计 / 汇报 | 说不清哪段设计生出了哪行代码 | 変換ログ：段 → Prompt → 代码，一一对应 |

# GitHub Copilot 仕様書が長すぎる場合の Token 節約と精度向上ベストプラクティス

作成：2026-10-09
位置付け：日本の大規模金融 IT 現場（証券／銀行／保険／JA・共済系の厳格なプロジェクト）を想定した実践資料です。Copilot の機能紹介ではなく、**「仕様書が長く、冊数が多い場合に、どう入力すれば Token を節約し、詳細を落とさず、幻覚（ハルシネーション）を防げるか」**という一点に答えるためのものです。
事例：すべて本 PoC の実案件 `JOJAMPG01W010`（JA向けマイページメニュー、PL／BL 詳細設計）を用いています。数値は実測値であり、模式的な例示数字ではありません。
関連資料：「Copilotと自研パイプライン：文書分割とToken比較」（Token 試算の詳細）、「確定性検索の仕組み解説」、「AIコード生成プロンプト_原文版用.md」（P0〜P4 プロンプト全文）。

> 結論を一言で言うと、**Token 節約の本質は「文書を圧縮すること」ではなく、「1 回の生成ごとに、その生成に本当に必要な原文のセクションだけを渡すこと」です。** 誰が分割するかでコストと精度が決まります。スクリプトによる分割（Token 0、監査可能）＞ 人手による分割（Token 0、ただし工数がかかり、原文との乖離が起きやすい）＞ LLM 自身に分割・検索させる（最も高く、書き換え・行落ちのリスクあり）。Copilot 自身には確定的な自動分割機能はないため、ベストプラクティスは、**分割と組み立ては Copilot の外側で人／スクリプトが行い、Copilot には「与えられたセクションの範囲内でコードを書くこと」だけを担当させる**ことです。

---

## 0. 前提：なぜ Copilot への「全量入力」が今は実際のコスト問題なのか

1. **課金方式が変わりました。** GitHub Copilot は 2026-06-01 から Token 課金（AI Credits、input／output／cached を別々に計量）に移行しました。定額制の時代は「ファイルを多めに添付する」ことは単に遅くなるだけでしたが、現在は会話の 1 ターンごとに添付量に応じて繰り返し課金されます。会話が長くなり履歴が積み上がるほど、過去に添付した全文に対して何度も支払うことになります。
2. **コンテキストは保管庫ではありません。** Copilot Chat／Agent のコンテキストは、システムプロンプト＋カスタム指示＋**ターンごとに蓄積される会話履歴**＋そのターンの `#file` 添付＋Agent のツール出力で構成されます。ウィンドウが満杯になると**初期の会話が自動要約**されます。要約で削られた設計書のセクションは「渡していない」のと同じであり、その後の生成コードは「印象」で補われることになります。これが金融現場で最も許容できない幻覚の発生源です。
3. **注意（attention）が分散します。** PL、BL、OW、定数一覧を同じセッションに詰め込むと、BL の処理が Controller に混入したり、別のメソッドのチェック条件が対象メソッドに混入したりします。文書が揃っているほど混入は深刻になります。**詳細設計の生成においては、「多く渡すこと」は「正確であること」と同義ではなく、むしろ逆です。**

本案件の規模（実測）：

| 文書 | 文字数 | 内容 |
|---|---:|---|
| PL仕様書（Controller） | 16,336 | クラス定義＋処理詳細 01〜07 |
| BL仕様書（Service） | 15,438 | クラス定義＋処理詳細 01〜02（うち処理詳細02 のみで 8,591） |
| OW定義シート（画面 DTO） | 5,584 | 項目定義 |
| OW定義シート DaoDto | 2,835 | DAO 用 DTO 定義 |
| 定数一覧（DUMMY 版、抜粋のみ） | 11,085 | 約 100 行。**実際の定数一覧は 2,000 行超** |
| **合計（実際の定数全量、共通部品仕様書は含まず）** | **51,278** | Java ファイル 15 件を生成する際に毎回全量を添付すると、input は概算で約 **64 万 Token** |

対照として、工程ごとにセクションを組み立てて同じファイル群を生成した場合は、input は概算で約 **7 万 Token**、全量方式の約 **1/9** です（試算の前提は関連資料を参照）。節約できるのは費用だけではなく、各ターンの応答速度と注意の集中度も含まれます。

## 戦略 1：文書の前処理 ― Excel を「セクション単位で取り出せる」Markdown にしてから生成する

### 原則

日本の現場の仕様書は大半が Excel で、1 冊の中に表紙、改訂履歴、クラス定義、複数の処理詳細、画面遷移、コード表、備考が同居しています。**Excel の原物をそのまま Copilot に渡さないでください。** セル結合、ページごとに繰り返されるヘッダー、脚注、バージョン列によって、モデルが行や列を読み違えます。前処理の目的は「要約」ではなく、**逐語で Markdown 化し、座標付きのセクションに切ること**です。

### 具体的な進め方

1. **逐語で転記し、要約しない。** シート単位で Markdown の表に変換し、行数・列数は原物と一致させ、空セルは空のまま保持し、結合セルは左上のセルにのみ内容を記載し、判読できない箇所は `（判読困難）` と明記します。転記者（人でも AI でも）が文字を推測してはいけません。要約が事実の源泉（source of truth）になってしまうと、その後の生成はすべて誤った土台の上に乗り、監査もできなくなります。
2. **文字数ではなく、構造の境界で切る。** 分割の単位は、シート／処理詳細番号／表です。1 セクション＝1 つの完結した意味の単位、例えば `BL.処理詳細02`、`BL.クラス定義.変数表`、`OW.項目定義.Select003DaoInDto` とします。固定文字数でのチャンキングはチェック表を真ん中で割ってしまうため、精度事故の温床です。
3. **各セクションに索引を付ける（人が表を作ってもよいが、スクリプトが望ましい）。** セクションごとに、出典ファイル、見出しパス、開始・終了位置、用途を一言で記録します。生成時は記憶に頼らず、Copilot 自身に探させず、索引に従ってセクションを取り出します。
4. **「設計の根拠ではない」部分を明確に切り分ける。** 表紙、改訂履歴、転記メモ、作業メモ等のセクションには印を付け、生成時は**除外**します。本案件で実際に踏んだ落とし穴として、転記メモの子セクションが P2 の入力に混入し、モデルが「転記者の説明」を設計内容として扱ってしまった事例があります。除外ルールは親見出しだけでなく子セクションにも適用しなければなりません。
5. **繰り返されるヘッダーは 1 部だけ残す。** Excel では処理詳細ごとに「画面ID／画面名／プログラムID／作成者」の表が繰り返されます。前処理で共通ヘッダーとして印を付け、入力を組み立てる際は 1 回だけ含めます。

### 効果

前処理は一度だけの投資です（本案件では 5 文書・計 88 表について、スクリプトで行列数の不一致 0 件を確認済み）。これが済めば、その後の生成は毎回「索引に従って 2〜5 セクションを取り出す」作業になり、「冊子全体を毎回運び直す」作業ではなくなります。

## 戦略 2：段階的なプロンプト ― 依存順に工程を分け、1 セッションでは 1 つのことだけを行う

### 原則

**1 つのセッションで「この設計書一式から全コードを生成してください」と指示してはいけません。** 金融現場のプログラムには依存関係の階層があり、生成順序は依存順序に従わなければなりません。さらに、工程ごとにセッションを分け、工程ごとに検収します。

### 標準的な工程分担（本 PoC の P0〜P4）

| 工程 | 実施内容 | 渡す入力 | 成果物 |
|---|---|---|---|
| **P0 完全性ゲート** | 生成前の検査：文書間の表記不整合、参照されているが未定義の部品／定数、処理内容と変数表の矛盾 | 全文書の**索引＋疑わしいセクションの原文**（2 段階：まず索引を走査し、次に疑わしい箇所を掘り下げる） | 問題一覧。**重大な問題がある場合は、まず現場に確認し、問題を抱えたまま生成しない** |
| **P1 DTO** | DTO クラスの生成 | OW定義シートのうち、**当該 DTO に対応するセクション** | DTO 1 件につき 1 ファイル。1 件ずつ検収 |
| **P2 Controller（PL）** | Controller の生成 | PL のクラス定義＋対象の処理詳細＋PL 変数表の全体（変数表は各処理詳細に分散しているため全量が必要。下記の事例参照） | Controller |
| **P3 Service（BL）** | Service の生成 | BL の対象の処理詳細＋クラス定義の変数表＋該当した定数行＋該当した共通部品のシグネチャ | Service |
| **P4 DAO** | DAO インタフェース／呼出部の生成 | BL の**呼出仕様ブロック**＋OW DaoDto の対応セクション | DAO インタフェース |

重要な規律：

- **1 Chat ＝ 1 メソッド（または 1 DTO）。** 生成が終わったら閉じるか、新規セッションを開きます。同じセッションで処理詳細を 7 件続けて生成してはいけません。後半のコンテキストには前半のメソッドのコードが積み上がり、混入と要約による欠落はここから発生します。
- **まず復唱させ、それからコードを書かせる。** 複雑なメソッドについては、1 ターン目では「処理手順＋チェック一覧表」の出力だけを求め（Java は書かせない）、人が設計書と照合して問題がないことを確認してから、2 ターン目でコードを書かせます。復唱ターンの Token は、「誤ったコード一式を生成して手戻りする」コストよりはるかに小さくなります。
- **手書きの順序と生成の順序を混同しない。** 人が手書きする順序は DTO → DAO インタフェース → Service → Controller（依存順）であり、AI の P1〜P4 の番号は生成バッチの順序です。現場で説明する際は区別しないと、作業者が誤った入力セクションを持ってきてしまいます。

## 戦略 3：コンテキストの制御 ― Copilot が「見えるもの」すべてを管理する

### 原則

Copilot のコンテキストには、添付した `#file` だけでなく、開いているエディタのタブ、会話履歴、カスタム指示も含まれます。**管理していない部分も、モデルは読み、課金対象となり、生成結果に混入する可能性があります。**

### 具体的な進め方

1. **`#file` にはそのターンのセクションだけを添付し、冊子全体は添付しない。** 添付するのは前処理で切ったセクションのファイル／範囲であり、`BL仕様書.md` の全文ではありません。判断基準はシンプルです。添付した各セクションについて「このセクションは、生成するコードのどの行に対応するか」を説明できること。説明できないセクションは添付しません。
2. **`.github/copilot-instructions.md` には「プロジェクト規約」だけを入れ、「設計内容」は入れない。** 規約とは、命名規則、Getter／Setter の記法、アノテーションの形式、Java／Spring のバージョン、例外処理の方針、TODO の書き方であり、どのターンでも必要で、全体でも数十行に収まります。設計内容（特定メソッドの処理フロー）をここに入れると、毎ターン全員分の Token が消費され、しかも容易に変更できません。テンプレートは付録 A を参照してください。
3. **再利用する工程指示はプロンプトファイル化し、毎回手入力しない。** `.github/prompts/P0-check.prompt.md`、`.github/prompts/P3-service.prompt.md` 等に grounding のルール（戦略 6 と付録 B を参照）を固定し、作業者は「対象：BL.処理詳細02」の 1 行を埋めるだけにします。Token 節約（長い指示を毎回貼らなくて済む）になるだけでなく、作業者ごとに指示の書き方がばらつくことを防げます。金融現場のレビューでは、ここは必ず問われる点です。
4. **無関係なタブは閉じ、`#codebase` は慎重に使う。** `#codebase` や Agent モードにリポジトリ内を自分で探させる方法は、何をどこまで探したかが監査できず、ツール出力がコンテキストに蓄積して繰り返し課金されます。「類似実装の参考を探す」用途には向いていますが、**設計書の確定的な検索には向きません**。設計書のセクションは、人／スクリプトが索引に従って渡さなければなりません。モデルに自分でめくらせてはいけません。
5. **長いセッションは早めに見切る。** 回答が「先ほどのメソッド」のロジックを引き始めたら、直ちに新規セッションを開きます。新規セッションのコスト（2〜5 セクションの再添付）は、長いセッションの累積課金と混入による手戻りよりはるかに安く済みます。

## 戦略 4：辞書型文書の部分参照 ― 定数一覧・共通部品・メッセージ一覧は「使う行だけ」を抜き出す

### 原則

日本の現場には「辞書型」の大規模文書が 3 種類あります。**定数一覧（本案件の実物は 2,000 行超）、共通部品仕様書、メッセージ一覧**です。共通する特徴は、1 つのメソッドが実際に使うのは数行から十数行にすぎないという点です。**冊子全体の添付は、現場全体で最大の Token の無駄です。**

### 具体的な進め方

1. **まず grep し、それから添付する。** 生成前に、今回の処理内容に現れる名前（定数名、部品名、メッセージID）を辞書の中で正確に検索し、該当した行だけを小さな表に抜き出して Copilot に渡します。本案件の実測では、P3 の組み立て時に BL に現れる定数をまず集計したところ、BL の処理内容は定数を**説明文で**参照しており（例：「検索画面遷移区分に定数、ブランクを設定」）、候補となった定数名 86 件は 1 件も直接は現れませんでした。
2. **検索で見つからない場合は TODO とし、値を推測しない。** 上記の状況は日本の現場では極めて一般的です。設計書に「定数、○○を設定」とだけ書かれ、定数の物理名／値が明記されていないケースです。正しい対応は、コードに `// TODO: 設計確認 — 定数名・値が設計書に明記されていない` と残し、未確認事項の一覧に登録することであり、**Copilot に「それらしく見える定数名」を作らせてはいけません**。もっともらしく作られるほどレビューで見抜きにくくなり、本番リスクが高まります。
3. **共通部品はシグネチャだけを渡し、仕様書全文は渡さない。** Copilot が必要とするのは「クラス名＋メソッドシグネチャ＋引数／戻り値」の 3 行であり、部品の内部処理フローではありません。本案件で追跡した連鎖の例を示します。

```text
PL.処理内容「変数.WebDTO初期化部品.initWebDto(...)」
→ PL.変数表「WebDTO初期化部品 → JOAKKBDtoUtil」
→ 必要な入力は、JOAKKBDtoUtil.initWebDto のシグネチャ 1 件のみ
```

シグネチャがまだ入手できていない場合（共通部品仕様書が未収集の場合）は、TODO としてください。メソッド名から引数を推測させてはいけません。
4. **抜粋表には出典を付ける。** 各行に「定数一覧 第○行／部品仕様書 ○章」と明記します。生成コードのコメントや変換ログから追跡でき、現場レビューで「この定数の根拠は？」と問われた際に即答できます。

## 戦略 5：チェック処理への特化 ― まず「チェック一覧表」を抽出し、それからコードを生成する

### 原則

詳細設計の中で Token 密度が最も高く、最も落ちやすいのは主フローではなく、**チェック処理**です。単項目チェック（必須、桁数、形式、コード値）、相関チェック（A と B の組み合わせ）、存在チェック（マスタ／端末構成情報の有無）、権限・状態チェックが該当します。これらは通常、入れ子になった番号（`3-6-2-1` のような 4 階層の番号）で処理内容の表の中に散らばっており、**全量を入力した場合にモデルが最初に落とすのがこの深い分岐です**。主フローは正しく見えるのに、テストで初めてチェックの半分が欠けていることが判明する、という事態は金融現場では致命的です（チェック漏れは、そのまま本番障害の候補となります）。

### 具体的な進め方

1. **チェックを独立した表にし、生成の中間成果物とする。** まず専用のプロンプト（対象の処理詳細だけを渡す）で Copilot にチェック一覧を抽出させます。列は、`チェックID／対象項目／条件／NG時の処理（メッセージID、例外、遷移先）／設計書の番号` とします。この表を人が設計書と 1 行ずつ照合します（照合コストは、表 1 枚とコード一式とでは比べものにならないほど表の方が安く済みます）。
2. **照合が済んだら、その表と元の処理セクションを一緒にコード生成ターンへ渡す。** あわせて、「チェック一覧の全行を実装すること。実装できない行は TODO にすること。一覧に無いチェックを足さないこと」と明示的に指示します。
3. **NG 時の処理にはメッセージID の原文を必須とする。** `JOCOMNG0165E` のようなメッセージID DEnum や定数名は、設計書から逐語でチェック表に写してください。Copilot に書き換えさせてはいけません。メッセージID が 1 文字違えば、実行時には別のメッセージになります。
4. **桁数・形式チェックは「条件の原文」を残す。** 例えば「半角2桁以外の場合」を、抜粋時に「length!= 2」と書き換えてはいけません。原文の「半角」という 2 文字が、全角→半角の判定が要るかどうかを決めるため、書き換えは情報の損失です。

完全な事例は次節を参照してください。

## 戦略 6：Grounding と生成後の検証 ― Token を節約しても「もっともらしく作る」ことは許容しない

### 原則

上記 5 つの戦略はいずれも「渡す量を減らす」ものですが、本戦略は「少なく渡しても、正確さは落とさない」ことを担保します。金融現場の鉄則は、**生成コードは入力セクションに明記された内容だけを使い、欠落・曖昧な箇所はすべて TODO＋設計確認とし、推測は厳禁**ということです。

### すべてのプロンプトに固定するルール（付録 B に全文）

```text
- 設計書に明記されていない定数名・値、メソッドシグネチャ、フィールド名は推測しないこと。TODOコメントとして残し、理由を書くこと。
- 転記メモは設計の根拠ではない。使用しないこと。
- 判読困難とマークされた箇所は TODO とすること。
- 入力として渡されたセクション以外の処理・チェックを追加しないこと。
```

### 生成後の 3 段階の検証（いずれも必須）

| 検証 | 実施内容 | 検出する問題 |
|---|---|---|
| **コンパイル検証** | `javac`／Maven で生成コードをコンパイルする | シグネチャの推測誤り、存在しない型、import の欠落 |
| **Grounding ホワイトリスト検証** | 生成コード内の定数名、部品名、メッセージID、DTO 項目名をスクリプトで grep し、入力セクションに現れたかどうかを 1 件ずつ逆引きする | 幻覚で作られた定数、項目、メソッド |
| **TODO の一覧化** | すべての TODO を表に抽出し、行き先（現場確認／次期設計書／部品仕様書待ち）を 1 件ずつ登録する | TODO が黙って消えること、誰も追跡しないこと |

修正には上限を設けます。自動／半自動の修正は最大 3 回までとし、3 回で収束しない場合は止めて人に報告します。Copilot に長いセッションで際限なく修正させてはいけません。修正のたびに Token を消費し、設計書の原文からもどんどん離れていきます。

## 戦略 7：Token の運用 ― 消費量を報告できる数字にする

金融現場の PoC では、最後に必ず「AI 生成にかかったコストと効果」を報告します。初日から次の 3 つの習慣を付けておけば、報告時に数字を作る必要がなくなります。

1. **工程ごとに記録する。** 生成のたびに、工程（P1〜P4）、添付したセクション（文字数）、生成ファイル、修正回数を記録します。これが変換ログとなり、監査要件も同時に満たします。
2. **実測の比較で語る。** 本案件の報告の言い回しは既に成立しています。「全量添付では約 64 万 input Token、分段組み立てでは約 7 万で約 1/9。全量方式では BL の処理が Controller に混入するリスクが見られたが、分段方式では発生していない」といった形です。
3. **プロンプトキャッシュを予算の前提にしない。** Copilot／API のキャッシュにより、繰り返されるコンテキストが安くなる場合がありますが、ヒットは制御できず、コンテキストが自動要約されれば無効になります。予算は「キャッシュなし」で見積もり、節約できた分は幸運として扱います。

# 中核事例：チェック処理が多い詳細設計を、どう入力すべきか

## 事例の背景

対象：`JOJAMPG01W010Service.doNoAction`（外部診断）、BL仕様書 処理詳細02。

このセクションが難しい理由は次のとおりです。

- 規模が大きい：1 セクションだけで **8,591 文字**、BL 全体の 56% を占めます。
- 構造が深い：処理内容の番号は 4 階層（`3-6-5-1-1-1`）まであり、変数 10 件、DAO 呼出 3 件（select001／002／003）を含みます。
- チェックが密集している（抜粋）：

| 設計書の番号 | チェック内容（原文の要旨） | NG 時／判定結果 |
|---|---|---|
| 3-5 | DAO取得001 の件数 ＝ 定数「検索結果件数 0件」か | メッセージID `JOCOMNG0165E`（システムエラー）を設定し、例外をスローする |
| 3-6-2 | 県番号の桁数チェック：半角2桁以外か | 組合合併チェックフラグ ＝ true |
| 3-6-3 | 組合番号の桁数チェック：半角3桁以外か | 同上 |
| 3-6-4 | 支所番号の桁数チェック：半角2桁以外か | 同上 |
| 3-6-5-1 | 入力組合区分 ＝ 全国本部 の場合：県番号が `"48"` か | 一致 → サービスOutDTO に分類コード「全国本部」を設定。不一致 → フラグ ＝ true |
| 3-6-5-2 | 入力組合区分 ＝ 県本部 の場合：県番号が `"01"〜"47"` か | 一致 → 分類コード「県本部」を設定。不一致 → フラグ ＝ true |

- 落とし穴もあります。処理内容の複数箇所に「定数、○○を設定」とだけ書かれ、**定数の物理名と値が書かれていません**。また、`アプリ共通エリア` は 8 回使われているのに変数表に宣言がなく、クラス名も未確定です。これらはいずれも「AI に推測させる」箇所ではなく、TODO／設計確認の対象です。

## ❌ 誤った／Token を浪費する入力方法

```text

PL仕様書、BL仕様書、OW定義シート×2、定数一覧（全2,000行超）、
共通部品仕様書を、すべて #file で同じ Chat に添付する。
タブには別の画面のコードも開いたままにしておく。


この設計書一式に基づいて、JOJAMPG01W010 の Controller と Service の
全コードを生成してください。定数が不明な場合は一般的な値で補ってください。
```

何が起きるか（いずれも同種のプロジェクトで実測された、または予見できる事故です）：

| # | 結果 | 原因 |
|---|---|---|
| 1 | **Token の爆発**：この 1 ターンの input だけで 5 万文字＋定数全量（実際の定数一覧は単体で本案件の他の文書の合計を大きく上回る）となり、その後も同じセッションで質問するたびに全量が繰り返し課金される | 全量添付 × 会話の蓄積 |
| 2 | **チェックの実装漏れ**：`3-6-2〜3-6-4` の桁数チェックは 1〜2 件しか実装されず、`3-6-5` の `"48"`／`"01"〜"47"` の判定は 1 行のコメントにまとめられる | 深い入れ子の分岐は、長いコンテキストの中で最初に注意から落ちる |
| 3 | **定数の捏造**：「一般的な値で補って」は幻覚への許可そのものであり、それらしい定数名と値が作られ、本物のコードに紛れ込むため、レビューで見抜きにくくなる | 指示が grounding の鉄則と正面から矛盾する |
| 4 | **階層をまたいだ混入**：Service の処理に Controller（PL）の画面遷移ロジックが混入する | PL／BL が同じセッションに共存する |
| 5 | **途中で要約される**：2 つ目のクラスの生成中にウィンドウの自動要約が発動し、前半の設計セクションが削られ、後半のコードは「印象」で書かれ始めるが、表面的には流暢なままである | 長いセッション＋大きな添付 |

この版のコードは「完成度が高く」見えますが、実際にはチェックの網羅性も定数の正しさも信用できません。**手戻りのコスト（生成コード一式を設計書と 1 行ずつ照合して確認し直す作業）は、段階的に生成するコストをはるかに上回り、Token も節約できていません。**

## ✅ 正しい／Token を節約できる入力方法（4 ステップ）

### ステップ 0：P0 ゲート（走査のみ、コードは生成しない）

```text
添付：BL.クラス定義＋BL.処理詳細02（原文セクション、約9,800文字）
プロンプト（.github/prompts/P0-check.prompt.md）：
設計書の不整合・未定義参照を洗い出してください。コードは生成しないこと。
特に：変数表に宣言のないエリア参照、定数名が明記されていない箇所、
呼出仕様はあるが DTO 定義が別紙にある箇所を番号付きで列挙すること。
```

事前に確認する成果物として、`アプリ共通エリア` に宣言がない → 設計確認、定数の物理名の欠落が数件 → TODO として予定、といった形で整理します。**既知の問題一覧を持って生成に入ることは、生成が終わってから問題に気付くことと比べて、桁違いに安く済みます。**

### ステップ 1：DTO を先行させる（P1／P4 の入力）

```text
添付：OW定義シート DaoDto のうち Select001／002／003 に対応する 3 セクション（約1,500文字）
＋ BL.処理詳細02 の呼出仕様ブロック 3 件
生成：JOJAMPG01Select001DaoInDto／OutDto、002、003 の計 6 クラス。1 件ずつ検収
```

DTO は後続の Service の「型紙」です。先に DTO を確定させれば、Service の生成時はクラス名を参照するだけで済み、OW の全文を改めて添付する必要がなくなります。

### ステップ 2：チェック一覧表を抽出する（抽出のみ、Java は書かない）

```text
添付：BL.処理詳細02 の原文セクション（8,591文字）
プロンプト：
処理詳細02 からチェック処理だけを抽出し、一覧表にしてください。
列：番号／対象項目／条件（原文のまま）／NG時の処理／メッセージID・定数（原文のまま）
コードは書かないこと。一覧に無いチェックを補わないこと。
条件に定数名が明記されていない場合は「定数名未記載」と書くこと。
```

この表を人が照合します（設計書との照合は約 15 分）。`3-6-2／3-6-3／3-6-4` の 3 件の桁数チェック、`3-6-5-1 "48"`、`3-6-5-2 "01"〜"47"`、`3-5 JOCOMNG0165E` がすべて表に含まれ、条件が原文のまま書き換えられていないことを確認します。

### ステップ 3：doNoAction という 1 メソッドだけを生成する（P3）

```text
添付（合計 約13,000文字。全量方式の約1/4 で、どのセクションも実際に使われる）：
- BL.クラス定義.変数表（aina／uina／messageBundle／DAO、約600文字）
- BL.処理詳細02 の原文セクション（8,591文字）
- ステップ2 で照合済みのチェック一覧表（約1,500文字）
- 定数の抜粋表：今回 grep で該当した定数行のみ（該当0件の項目は TODO の指示として明記）
- 共通部品シグネチャの抜粋：uina／aina／messageBundle の使用メソッドのみ
（シグネチャ未入手の部品は「TODO：部品仕様書待ち」と指示）

プロンプト（.github/prompts/P3-service.prompt.md）：
JOJAMPG01W010Service.doNoAction だけを生成してください。
- チェック一覧表の全行を実装すること。追加のチェックを足さないこと。
- 定数名・値が設計書に明記されていない箇所は TODOコメントにすること（推測禁止）。
- DAO呼出は呼出仕様ブロックの通りにし、DTO は生成済みクラスを参照すること。
- 生成後に、処理内容の番号とコードの対応を自己申告リストとして添えること。
```

生成後は、戦略 6 の 3 段階の検証を実施します。コンパイル → ホワイトリストの grep（定数名／メッセージID／項目名を入力セクションに 1 件ずつ逆引き）→ TODO の抽出と一覧への登録、です。

### 両方式の比較

| 観点 | ❌ 全量一括 | ✅ 段階方式（本節） |
|---|---|---|
| 1 セッションの input | 5 万文字＋定数全量 2,000 行超 | 1 ステップ当たり 1,500〜13,000 文字 |
| ファイル 15 件生成時の input 概算 | 約 64 万 Token | 約 7 万 Token（約 1/9） |
| チェックの網羅性 | モデルの注意に依存し、何が落ちたか分からない | チェック一覧表で先に固定し、1 行ずつ照合できる |
| 定数が不明な場合 | 指示で「一般的な値で補う」ことが許可され、捏造される | TODO＋設計確認となり、問題が可視化される |
| 誤りの特定 | コード一式を 1 行ずつ再確認する | どのステップ、どのセクション、どの表かまで特定できる |
| 監査／報告 | どの設計セクションがどの行を生んだか説明できない | 変換ログ：セクション → プロンプト → コード が 1 対 1 で対応する |

# 付録 A：`.github/copilot-instructions.md` テンプレート（日本語・規約のみ）

```markdown
# プロジェクト規約（生成コード共通）
- 言語：Java（バージョンはプロジェクト pom に従う）、Spring のアノテーション記法は既存 Controller / Service に倣うこと。
- 命名：プログラムID を接頭辞とする既存命名（例：JOJAMPG01W010Service）に合わせること。
- Getter / Setter の記法、DTO のフィールド定義方式はプロジェクト規約に従うこと（未定の場合は TODO とすること）。
```

# 付録 C：自研パイプラインとの関係

本資料が扱うのは、**現場のツールが既に Copilot である場合に、どう使えば節約でき、正確になるか**です。
PoC で自動化と監査可能性そのものを検証するのであれば、最も Token を節約できる形は依然としてハイブリッド方式です。**分割と組み立てはローカルのスクリプトで行い（確定的、Token 0、変換ログあり）、最後の生成の呼び出しだけを Copilot に任せる**形であり、Copilot 自身に分割させたり探させたりする形ではありません。試算の比較は「Copilotと自研パイプライン：文書分割とToken比較」を参照してください。
