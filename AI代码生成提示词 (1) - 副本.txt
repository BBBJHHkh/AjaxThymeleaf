# AI コード生成プロンプト集（HH 現場 PoC 用）

## 使用方法

1. まず **P0** で設計書が揃っているか確認する（日本現場の要求：すべて設計書記載準拠。不足分は先に補う）。
2. **P1 → P4** の順に使用する：DTO → Controller → Service → DAOインタフェース。
3. 各プロンプトはコピーして使用し、`[]` の入力を対応する Markdown ドキュメント全文に置き換える。
4. プロンプト本文は日本語。生成コード中の識別子・コメント言語は設計書原文に厳密に従う（日本語部分は日本語のまま）。

## 入力説明（改訂、案A）

- **原文版**（`原文版/`）：唯一の事実源。Excel シートを原文のまま転記する。レイアウトを変更しない。
- **構造化版**：派生的な作業用コピー。P0～P4 プロンプトの実際の入力であり、『設計書Markdownテンプレート.md』の変換仕様に従い原文版から変換する。変換ログは各ファイル末尾の `## 変換ログ` を参照。
- 各プロンプトの「入力」は構造化版を指す。内容に疑義がある場合は原文版（および原本写真）に立ち返って確認し、推測してはならない。

1. 入力ドキュメントに明記された内容のみ使用する。ドキュメントに記載がなく、ドキュメントから直接導出もできない内容は、いっさい捏造してはならない。
2. クラス名、メソッド名、フィールド名、アノテーション、アノテーションパラメータ、パッケージ名、定数値、SQLを捏造してはならない。

5. 命名、パッケージ構成はドキュメント原文に厳密に従い、いかなる「最適化」や書き換えも行わない。

## P0：設計書完全性チェック

**用途**：コード生成前に、設計書が揃っているか確認する。**入力**：PL/BL/OW の Markdown（単体・複数可。ドキュメント名を明記）。

**プロンプト本文**：

```
# ロール
あなたは日本SIプロジェクト（HH現場）の設計書レビュー担当であり、SS/PS工程の設計書規約に精通している。

# タスク
以下の設計書が「AI コード生成入力」としての完全性を備えているかチェックする。チェックのみ行い、コードは生成しない。

# 入力
[PL仕様書 / BL仕様書 / OW定義シート の Markdown 全文をここに貼り付ける。
複数ドキュメントを同時にチェックする場合は「PL+OW」または「BL+OW」でグループ化し、各ドキュメント名を明記すること]

# チェック項目
1. クラス定義の完全性：クラス名、パッケージ名、メンバー変数（名／型／修飾子／アノテーション）は揃っているか
2. メソッドの完全性：各メソッドのメソッド名、引数（名／型／アノテーション／I/O）、戻り値は揃っているか
3. 参照の完全性：処理内容で参照される各変数、DTO、共通部品、定数は、変数表／DTO定義／ドキュメント内の他箇所で定義されているか
4. DTOの完全性（OW）：PL/BLで参照される各DTOのフィールドは、OWのマッピングマトリクスで定義されているか
5. 内部一貫性：同一概念がドキュメント内の複数箇所に現れる場合、名称・型は一致しているか

# 出力要件
- 「欠落項目」と「矛盾項目」の2分類で箇条書きにし、各項目に記載すること：問題内容、ドキュメント内の位置、コード生成のどの部分に影響するか
- 最後に結論を示す：「生成条件を満たす」または「満たさない」。満たさない場合は、先に補完すべき内容リストを示す
- ドキュメント内容のみに基づいて判断する。「～かもしれない」と推測したり、欠落情報を補完したりしてはならない
```
